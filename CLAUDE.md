# Jhapat (झपट)

Sachin's web app for a Nepali party game. Items such as paani, phool, chiya, paisa, chithi and maya sit on a table. The player drops into a random song 7–10 s before one of those words is sung, and the crowd grabs and referees in real life. It is a music player, not a scoring app: no scores, no timers, no rules engine.

Live at https://sachdq.github.io/jhapat/ (GitHub Pages, `main` branch, repo root). Pushing to `main` deploys in about a minute. Pages sends `max-age=600`, so add `?v=<commit>` to the URL to see a new version straight away. Push over SSH (`git@github.com:SachDQ/jhapat.git`); there's no `gh` CLI or HTTPS credential on Sachin's Mac.

Versions keep Sachin and Claude in step: run `npm run bump` before each push that changes a page (not for docs-only commits). It raises `VERSION` in both pages and `version.json` together (the tests check they match). The player shows it at the bottom, the studio next to the logo. A page that finds a newer `version.json` on the site shows a "New version · Reload" button, which reloads with `?v=` past the cache. When telling Sachin what to test, name the version he should see.

## Layout
- `index.html`: the party player, a single file with no build step. It plays YouTube through the IFrame API in two stacked players: the front one plays, the back one loads the next drop muted. iPhone, iPad and Safari use one player, because they only give sound to a video the person has tapped. Flow: pick a playlist (official ones from `playlist_cards`; the list is skipped when there's only one) → Play screen shows only that playlist's items with counts → Start. In localStorage (`jhapat.v1`): `S.cards` (the playlist list), `S.bundles` (every playlist opened, for offline), `S.tables` (items turned on per playlist; only real toggles are stored), `S.chosen`. A playlist opened for the first time also turns on any item every one of its songs has. Items take even turns: the next drop picks an item first (every item on the table with a song for it is equally likely, so Maya, in most songs, gets no more drops than Chithi), then one of its songs not played yet; an item whose songs have all played reuses the one played longest ago, and the last three songs never come back. Drops: the run-up is random in 7–10 s and never reaches back past an earlier table word (1.2 s kept after it, since a tag marks where the word starts). A repeated line counts once (`[item, t, rep]` in the bundle): its word drops in before the repeat with the most room; repeats that all have the full run-up take turns. The 16 songs built into `seed()` are only a fallback for phones that have never reached the database. Kept short on purpose: the video box stays folded until the first song plays, Start stands alone until then, a long item list shows its first 8 (plus any that are on or were tapped) and "+N more", run-up and video options sit in one folded Settings card, and playlist cards fan out their first songs' covers (`playlist_cards.thumbs`, YouTube's `mqdefault.jpg`).
- `studio/index.html`: the tagging studio, for editors only. It uses supabase-js 2.45.4 (UMD; verified live with the publishable key) and signs in by email link. It searches LRCLIB for timed lyrics, folds repeated lines together, highlights item words, and supports Hear/Tap/nudge per word with the timing copied to every repeat. A tap is refused unless it lands from 1 s before a repeat's line to 0.5 s after the next line starts. It also handles upload length checks (within 2 s of the lyrics → synced) and sync, items and playlists. Untimed lyrics get **Time the lines**: play the upload and tap as each line starts (Again for a line sung more often than it's written, Skip for one that isn't sung, Undo); the taps become timed lines, every item word is auto-tagged from them, repeated lines group themselves, the upload counts as synced and a draft goes live as auto. Item-by-item tap-along stays for songs with no lyrics at all (folded away when there are words to time). Item words are coloured by state (dashed = not tagged, light gold = estimated, gold = timed or checked by ear); "Auto-tag them" estimates every untagged one, and Items › "Auto-tag all songs" does it everywhere after a new item or spelling. **Check tags** plays each word (a chorus once, at its roomiest repeat) from 3 s before with a countdown; Right marks it checked, Earlier/Later moves every repeat. **Add many** (`#import`) takes `Title - Artist | YouTube link | m:ss` lines, measures each upload in a muted off-screen player, picks LRCLIB's version of the same length, auto-tags it and sets status `auto`; the rest come in as drafts. A line can end with `| lrclib:12345` to use that exact LRCLIB version (fetched by id, one request, no search). LRCLIB allows about 45 requests a minute from a browser and 90 from a script with its own User-Agent, per IP, so the studio spaces requests 1.4 s apart and a "too many requests" answer waits for its Retry-After and asks again; a row it never answers is marked and left out of Add, and "Find again" looks up only those rows. Don't run other LRCLIB scripts from the same computer while Add many is working.
  Lists stay short: Songs has covers, item counts per song, a search, status filters (Auto, Tagged, Checked, Drafts, Needs work), a playlist filter and a sort. Items are tiles (first 12, then "Show all") with one editor that opens above them; New item and Auto-tag all songs sit at the top. Playlists are folded cards with covers; open one to rename, reorder, take songs out (✕) or add them by typing. On a song, the Uploads and Playlists cards fold to a one-line summary (Uploads folds itself while its first upload is synced), and "Only lines with item words" hides the rest of the lyrics. Folds, the song sort and that switch are remembered in localStorage (`jhapat.studio`); filters reset on reload.
- `db/schema.sql`: tables, row-level security, `playlist_bundle(pid)` and the `playlist_cards` view (its `thumbs` column, the first four songs' uploads, was added on 13 Nov). `db/seed.sql` holds the 16 starter songs. Both were run once in the Supabase SQL editor; edit them, then re-run the changed parts there.

## Data rules
- Tag times are on the lyrics' timeline. Each upload (`videos.offset_s`) stores how far it runs behind the lyrics, so video time = lyric time + offset. Never re-tag because an upload changed; fix that upload's offset.
- `songs.status`: draft (hidden) → auto (tagged automatically from lyrics the same length as the upload; public) → tagged (someone tagged or timed by hand) → checked. Tagging by hand moves draft or auto to tagged.
- `tags.rep` is the first line of the tag's repeated-line group (null for tap-along tags); the studio writes it with `line` and `word`.
- Item spellings (`items.words`) match at the start of a lyric word, in Devanagari and roman letters. A spelling starting with `-` rules words out for that item (`-दामी`, `-full`, `-रातो`). Don't add short roman spellings that are common words: roman `pani` was dropped from Paani because it's usually पनि (also). `items.emoji` shows on chips; `items.note` is the prop to put out.
- Lyrics live in the database and are fetched from LRCLIB at runtime. Don't copy lyrics into the repo, tests or docs. Test fixtures use invented lines.

## Adding songs (the process)
1. Sachin sends a list of songs. Claude finds an upload for each in his Chrome (YouTube search results carry each video's length): prefer "Artist - Topic" or official audio, then the official video. Check embedding with `https://www.youtube.com/oembed?url=…` (401 = blocked).
2. Paste `Title - Artist | https://youtu.be/ID | m:ss` lines into studio › Songs › Add many, pick a playlist, Find, check the picks (LRCLIB's version with the same length is chosen), Add.
3. Same length → live as `auto`, every item word tagged. Otherwise a draft: sync by ear, or tap along when LRCLIB has no timed lyrics.
4. Polish with Check tags on the phone or laptop.

Many songs at once (how 172 were added on 13 Nov 2026), from the terminal plus Add many:
- Track lists: Spotify's embed page `https://open.spotify.com/embed/playlist/<id>` holds the first 100 tracks with lengths in its `__NEXT_DATA__` JSON (the web player, signed in, has the rest). YouTube Music playlists come from its web API (`music.youtube.com/youtubei/v1/browse`, client `WEB_REMIX`); its search with the "songs" filter (`params: EgWKAQIIAWoKEAkQBRAKEAMQBA==`) returns the Topic uploads with their lengths, which match Spotify's to the second. Plain YouTube search buries them.
- For each song: the Topic upload of the same length (±2 s), LRCLIB timed lyrics of that length whose artist shares a name with the song's (a cover's timing would be off), lyrics that are actually Nepali (Devanagari or common roman Nepali words; a Turkish song once sat in a "Nepali" playlist), oEmbed 200, and at least one item word. Only those go in, so every one lands as `auto`.
- Give each line its `| lrclib:<id>` so Add many takes that version instead of searching. Shorten titles that contain " - " (it splits Title - Artist).
- LRCLIB rate-limits by IP: keep scripts under about 75 requests a minute with an own User-Agent, honour Retry-After, and run one copy at a time (two copies once doubled the load). Its database dump would avoid the limit but is 49 GB compressed (Oct 2026), more than the Mac's free space. LRCGET is a desktop app for tagging local music files through the same API, so it doesn't help. Add many takes about 1.4 s a song to find and 1.7 s to add; 100 at a time is fine.
